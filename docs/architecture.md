# 🏛️ Butler: System Architecture

This document details the software engineering and design decisions underpinning the Butler persistent multi-agent memory system.

---

## 1. Core Architectural Principle

> **"Events are truth. State is cache."**

Butler completely separates **ephemeral session activity** from **durable project memory**. It achieves this through an **event-sourced architecture** combined with **incremental materialized view caching**.

Instead of storing volatile database rows that represent the current state of a task or wiki page, Butler writes immutable, append-only records of things that *happened*. 

```text
       Write Operations (Tools)                   Read Operations (Resources)
              │                                                ▲
              ▼                                                │
       [ Appended Events ]                             [ State Cache ]
              │                                                ▲
              ▼                                                │
   🗄️ SQLite Append-Only Log  ──(Materialized Reducer)──► Incremental Replay
```

### Benefits of Event Sourcing in Multi-Agent Systems
*   **Volatile Session Recovery:** If an agent window crashes mid-task, Butler does not lose historical progress. Replaying the event stream recreates the exact state.
*   **Auditability & Logs:** You can trace the exact order in which code changes, constraints, or decisions were recorded.
*   **Conflict Resolution:** Optimistic version locking prevents concurrent agents from overwriting task completions based on outdated state references.

## 2. Component Design

Butler's internals are divided into highly focused modules:

```text
Transport (MCP Server Stdio)
       ↓
Dispatcher (Routing calls to tools & resources)
       ↓
┌─────────────────────────────────┐
│       Session Coordinator       │ 💓 Presence registry, heartbeats, & stale timeouts
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│        Event Log Store          │ 📝 Safe database transactions & appends
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│       State Materializer        │ ⚡ Incremental state cache & snapshotting
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│      Universal Memory Engine    │ 🔍 Pure-JS TF-IDF search & vector retrieval
└─────────────────────────────────┘
```

### A. Transport & Dispatcher Layer
*   **MCP Protocol Server:** Exposes standard stdio transports complying with the Model Context Protocol SDK.
*   **Resource Handlers:** Exposes structured, dynamic markdown and JSON context templates (e.g. `butler://projects/{id}/context`).
*   **Tool Dispatcher:** Routes incoming JSON-RPC client requests (e.g., `todo.add`, `rule.add`, `session.heartbeat`) to backend database procedures.

### B. Session Coordinator
*   **Registry:** Tracks active agent clients (`status = 'alive' | 'stale' | 'dead'`).
*   **Heartbeat Monitor:** A background thread sweeps the database every 15s. Sessions with missing heartbeats are marked as `stale` (60s) and then `dead` (300s).
*   **Handoff Generator:** When a session is declared dead or disconnects, this coordinator queries only the events generated by that session and materializes a structured continuity marker in the event log.

### C. State Materializer & Incremental Cache
*   **Reducers:** Replays events (`TODO_CREATED`, `TODO_COMPLETED`, `WIKI_UPDATED`) to build `ProjectState`.
*   **Incremental Caching:** To avoid high-overhead replays from the beginning on every query, Butler maintains an in-memory deep-copied cache of the last materialized state. When a read occurs, Butler queries and plays *only* events appended *since* the last cached event ID.
*   **Snapshots:** Every 100 events or every 30 minutes, Butler serializes a JSON snapshot to disk, truncating replay lookup costs for fresh startup sequences.

### D. Memory Indexing Engine
*   **Zero-Config Retrieval:** Uses local, highly optimized sparse keyword matching (TF-IDF vector projections). It runs natively in JavaScript with 0 compilation dependencies.
*   **Hybrid Vector Engine:** Retains support for dense vector mappings (cosine similarity on Float32 arrays) in case the editor agent computes embeddings before submitting.

## 3. Database Design

Butler uses a single SQLite file located at `.butler/butler.db` inside your project root. 

### Performance Optimizations
1.  **Write-Ahead Logging (WAL):** Enables multiple parallel readers to execute simultaneously while a write is occurring, preventing blocking bottlenecks.
2.  **Synchronous NORMAL:** Offers a highly resilient write profile with minimal disk-flush latency.
3.  **Performance Indexing:** Indexes on compound columns (e.g. `idx_events_project_session` on `(project_id, session_id)`) avoid $O(N)$ lookup scans.
4.  **Database-Backed Sequences:** A dedicated `sequences` table handles safe, race-free incrementing IDs inside SQLite transactions, resolving race conditions from concurrent workers.

```sql
-- Schema Overview
CREATE TABLE IF NOT EXISTS projects (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT (strftime('%s', 'now'))
);

CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  client_type TEXT NOT NULL,
  status TEXT CHECK(status IN ('alive', 'stale', 'dead')) DEFAULT 'alive',
  last_heartbeat INTEGER NOT NULL,
  last_event_seen INTEGER DEFAULT 0,
  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);

CREATE TABLE IF NOT EXISTS events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id TEXT NOT NULL,
  session_id TEXT NOT NULL,
  type TEXT NOT NULL,
  payload TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT (strftime('%s', 'now')),
  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);
```
